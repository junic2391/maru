**이 명령은 `/ai-log`보다 먼저 실행한다.** CJ ENM 채용 공고가 "AI 코드 리뷰를 개발 흐름에 적용"하는 것을 팀의 기술 환경으로 명시한다 — 이 명령이 그 경험을 실제로 만든다. 여기서 나온 지적 사항을 수용·거부한 이력이 있어야 뒤에 실행하는 `/ai-log`의 "위임한 범위 / 거부한 제안과 이유"가 채워진다.

현재 브랜치와 base(main) 사이의 `git diff`, `git log`를 근거로 **리뷰어**로서 diff를 읽는다. 이번 세션에서 이미 작성에 관여한 코드라도, 리뷰 단계에서는 새로 들어온 코드를 처음 보는 사람처럼 비판적으로 본다.

## 점검 순서

1. **방어 구역 위반 확인**: `.claude/defense-zones.json`에 걸리는 경로가 diff에 포함돼 있으면, 그건 AI가 초안을 쓰면 안 되는 영역이다 — 실제로 사용자가 직접 작성했는지 diff 내용으로 짐작해보고, AI가 작성한 것으로 보이는 부분이 있으면 가장 먼저 지적한다.
2. **정확성**: 로직 오류, 엣지 케이스 누락, 타입 안전성(`any` 사용 여부)
3. **계약 일치**: 데이터/통신 코드가 바뀌었으면 `ws-contract` 스킬의 현재 Phase 계약과 일치하는지, `@maru/shared-types`가 아닌 곳에서 타입을 새로 정의하지 않았는지
4. **보안**: `security-checklist` 스킬의 두 표 기준으로 이번 diff에 해당하는 항목이 있으면 확인
5. **디자인/카피 일관성**: UI 변경이 있으면 `design-tokens`(semantic 토큰만 참조했는지)·`brand-voice`(마이크로카피 사전 사용 여부) 기준
6. **불필요한 범위 확장**: 요청받지 않은 리팩토링·추상화·주석이 섞여 있지 않은지

## 출력 형식

발견한 항목을 심각도 순으로 표로 출력한다(파일 저장 없이 그 자리에서):

| 파일 | 지적 사항 | 근거 |
|---|---|---|
| ... | ... | ... |

문제가 없으면 "지적 사항 없음"이라고 짧게 답한다. 지어낸 지적을 만들지 않는다 — diff에 실제로 존재하는 근거만 쓴다.

리뷰가 끝나면 사용자에게 각 지적을 반영할지 물어본다. 반영하지 않기로 한 지적이 있으면 `/reject`로 그 순간 기록할지 안내한다.
