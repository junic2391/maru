# tutorial-format

원본: `/Users/junic/Documents/workspace/projects/maru-journal/tutorial/M1-02.md`, `M1-03.md`가 이 양식이 나오기 전에 쓰인 실전 검증 사례다. 이 스킬은 그 경험(2026-09-11 피드백 — NestJS 예시 코드가 실제로 실행되지 않는 설계 스케치였던 사고, `docs/ai-rejections.md` 참고)에서 출발했다. 다만 그 사고의 재발 방지책은 "작성 전 실행"이 아니다(2026-09-17 개정) — 프레임워크·라이브러리가 실제로 요구하는 API 계약·타입 시그니처에 맞게 논리적으로 쓰는 것으로 충분하다. 틀린 부분은 사용자가 태스크를 실제로 진행하며 겪는 순간 그 자리에서 고친다. 기존 두 파일도 아래 헤더 필드·의존 관계 형식화는 아직 반영 전이다(재편 대상).

**이 스킬은 새 tutorial 문서를 쓰는 것이 기본 시나리오다.** 이미 있는 문서의 Step을 고치는 것도 가능하지만, 그때도 아래 원칙(특히 "이상적 순서")을 기준으로 판단한다 — 기존 서술을 보존하기 위해 원칙을 굽히지 않는다.

**이 문서의 독자는 비전공·경력 공백에서 직접 손으로 치며 배우는 사람이다** — Step 태그([배관]/[핵심]/[검증])와 [핵심]의 원리·스스로 확인은, 원리 파악 없이 코드부터 따라 치는 순서를 뒤집고 자가 검증을 Step마다 분산해 작은 성공 경험을 쌓게 하려는 장치다. "왜 이렇게 결정했는가"는 쓰지 않는다 — 그건 `Build-Phase*.md`([[phase-doc-format]])의 "설계 결정과 트레이드오프"가 정본이다. **여기서 "왜"를 다시 서술하면 두 문서가 따로 논다.** 필요하면 링크만 건다.

> ▎ 단 하나의 예외: [핵심] Step의 원리는 이 규칙 밖이다 — 트레이드오프·대안 비교·면접 답변이 아니라, 이 Step 하나가 존재하는 이유를 1~3문장으로 압축한 것이다. Glossary.md(가장 짧은 설명)와 guide의 설계 결정과 트레이드오프(가장 깊은 설명) 사이의 얇은 중간층이라고 본다. 대안 비교나 "왜 그 이유가 맞는가"까지 들어가면 이 예외를 벗어난 것 — 그건 guide로 보낸다.

## 파일 규칙

- 경로: `maru-journal/tutorial/M1-XX.md`. 파일명은 태스크 ID만(부제는 문서 첫 줄에).
- 세션:태스크는 1:1. 하나의 M1-XX = 하나의 tutorial 파일 = 하나의 세션.
- `.gitignore` 대상 — 버전관리하지 않는다. 문서 맨 끝에 다음 각주를 그대로 남긴다: `*이 문서는 버전관리되지 않습니다. 막히는 자리를 만나면 그 자리에서 고쳐 쓰세요.*`
- **Step은 실제 레포 코드를 옮기는 게 아니라 "이상적으로 순서대로 지었다면"을 기준으로 쓴다** — 이미 완료된 태스크(Phase 0 등)도 예외 없다. 레포 코드가 이 태스크의 몫을 나중 태스크로 미뤘더라도, 튜토리얼에서는 이 태스크 범위 안에서 바로 닫힌 것처럼 쓴다 — 뒤 문서가 앞 문서를 전제하거나 앞 문서가 "이건 뒤에서 다룬다"고 미루면 안 된다. 단, guide 문서에 이유와 함께 명시된 **의도된 설계 범위**(예: "이 타입은 M1-02가 채운다")는 그대로 둔다.
- **코드는 실행해서 사전 검증하지 않는다** — API 계약·타입 시그니처에 맞게 논리적으로 작성하면 충분하고, `git checkout` 원복이나 실행 출력 캡처는 두지 않는다. "여기까지 확인"의 기대 출력도 추론한 값이다 — 틀리면 사용자가 태스크를 진행하며 그 자리에서 고친다(문서 끝 각주가 그 경로).
- 방어 구역 태스크는 실제 코드를 싣지 않는다 — 제네릭 예시 + 백지 재현으로 대체한다("변형 — 방어 구역형" 참고). "치는 것"이 코드가 아닌 태스크(물리 기기 재현, 문서·계산 작성)는 "변형 — 스파이크형"·"변형 — 집필형"을 쓴다(문서 골격 뒤에 있음).
- 위임 구역·방어 구역 판단 같은 AI 운영 이야기는 넣지 않는다 — 학습 흐름을 끊는다. `Workflow.md` 소관.

각 Step 제목 끝에는 태그가 붙는다. 태그마다 구성이 다르다.

| 태그 | 뜻 | 포함 요소 |
|---|---|---|
| **[배관]** | 설치·설정. 원리를 몰라도 무방 | 치는 것 → 눈여겨볼 줄(0~2개, 선택) → 여기까지 확인 |
| **[핵심]** | 이 태스크의 존재 이유. 원리를 스스로 설명할 수 있어야 통과 | 원리 → 치는 것 → 눈여겨볼 줄(1~4개) → 여기까지 확인 → 스스로 확인 |
| **[검증]** | 만든 것을 확인만 하는 단계 | 치는 것 → 여기까지 확인 |

공통: **치는 것**은 파일 경로 + 그대로 옮길 코드. **눈여겨볼 줄**은 복붙으로 끝나지 않게, 왜 이 줄이 없으면 깨지는지(개수는 태그별로 다름, 위 표 참고). **여기까지 확인**은 명령 + 정확한 기대 출력 — **통과하지 않으면 다음 Step으로 가지 않는다.**

"## 이 문서를 읽는 법" ~ "### 시작 전 상태 확인"은 표준과 동일하다. Step 부분만 다음으로 바꾼다:

- **ADR 작성류**: Step을 "산출물 단위"(ADR 한 건 = Step 하나)로 나눈다. 매 Step이 [핵심]이다 — 이 결정이 왜 이렇게 났는지 스스로 설명 못 하면 ADR을 옮겨 적은 것에 불과하기 때문이다. `adr`/`adr-format` 스킬의 5단 구조(배경·고려한 선택지·결정·이유·결과)를 "치는 것" 자리에 그대로 쓴다 — 코드 대신 ADR 본문이 "치는 것"이 된다.
- **리서치+계산류**: Step을 "공식/기준 정하기 → 후보 조사 → 결정 → 표 채우기" 순서로 나눈다. 공식을 유도하는 Step은 [핵심], 후보를 기계적으로 비교표에 채우는 Step은 [배관], 최종 표를 채우고 "이 가정이 깨지는 지점"을 적는 마지막 Step은 [검증]이다.

두 갈래 모두 "여기까지 확인"은 명령 실행이 아니라 **guide 문서의 DoD 문장과 결과물을 나란히 놓고 일치하는지 확인하는 것**으로 대체한다(예: "`Plan.md` 9-2 표의 빈칸이 다 채워졌는가").

## 변형 — 방어 구역형

<!-- "치는 것"이 실제 상태/전이 로직이면 싣지 않는 태스크(예: WebRTC 연결 상태 머신). 실제 설계는 독자가 직접 채우고, 문서는 문법과 순서만 가르친다. -->

"## 이 문서를 읽는 법" ~ "### 시작 전 상태 확인"은 표준과 동일하다. [배관]/[핵심]/[검증] 태그도 그대로 쓴다 — 다만 [핵심] Step 안에서 "치는 것"의 의미가 달라지고, 마지막에 표준에 없는 Step 하나(백지 재현)가 추가된다.

- **[핵심] Step의 "치는 것"은 실제 설계가 아니라 도메인 무관 제네릭 예시다.** 신호등·카운터처럼 이 태스크의 실제 대상(통화 상태 등)과 무관한 소재로 문법·패턴만 보여준다. 그 문법을 실제 설계에 적용하는 건 독자의 몫이다.
- **"치는 것" 뒤, "여기까지 확인" 앞에 "할 일"을 추가한다.** 제네릭 예시로 익힌 문법을 방어 구역 안의 실제 파일에 적용하라는 지시문이다 — 몇 개를 만들지, 무엇을 채울지는 여기서도 답을 주지 않는다("네가 그린 상태 5개를 `types.ts`에 옮긴다" 정도로, 개수나 이름은 guide도 이 문서도 대신 정하지 않는다).
- **문서 설정용 파일(`defense-zones.json`, ADR 등)은 방어 구역이 아니므로 실제 내용을 그대로 싣는다.** 방어 구역은 "실제 상태/전이 로직"이지 그걸 보호하는 설정 파일이 아니다.
- **마지막 Step은 "백지 재현"이다** — [핵심]이지만 표준 구성(원리 → 치는 것 → 눈여겨볼 줄 → 여기까지 확인 → 스스로 확인)을 쓰지 않는다. 코드를 "치는" 게 아니라 기억에서 "재현"하는 단계라서다. 대신 **원리 → 재현 절차(번호 목록) → 스스로 확인**으로 구성한다: 에디터를 닫고 시간을 두고(다음 날 등) 백지에서 다시 그리고 다시 쓴 뒤, 원본과 비교해 "틀린 곳"이 아니라 "왜 그렇게 했는지 설명 못 하는 곳"을 찾는다.
